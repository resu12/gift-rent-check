# Background price monitoring

The cloud worker refreshes the private owner's saved gifts and checks enabled price rules while the dashboard is closed. It can add suggestions to the approval queue. It cannot approve, sign, submit, or automatically change a rental price. Open the app to review a proposal and approve its transaction in your wallet.

This first version serves only the configured private owner. It does not enumerate public users or run their policies. Paused rules and disabled gifts stay paused. Existing provider limits, ownership checks, saved-data checks, storage limits, and wallet approval safeguards still apply.

The dashboard's **Status → Monitoring** card shows enabled gift monitoring, pending approvals, the latest saved cloud result, and when the next check becomes eligible. Open its details for the last run and last fully successful check. **Manage rules** opens the existing rule controls and approval queue. The card reads saved status once a minute while the Status page is visible; **Refresh status** only reloads that information and does not launch a cloud run, collect provider data, or request wallet approval. A missing cloud record means no cloud check has been reported for that account, not proof that the GitHub schedule is disabled.

## How it runs

Telegram hosting has no scheduler exposed by the repository's current deployment tools. The optional [Cloudflare scheduler](cloudflare-scheduler.md) supplies an independent wake-up every 15 minutes, at minutes 7, 22, 37, and 52 UTC. It dispatches only `resu12/gift-rent-check`'s `background-monitoring.yml` workflow on `main`, with `scheduled: true`. The workflow's own hourly GitHub schedule, at minute 37 UTC, remains a fallback. The Cloudflare trigger must be separately deployed and activated; committing its files or publishing the Telegram app does not activate it.

Both triggers use the same GitHub job and the same saved monitoring checkpoints. The worker starts a new automatic check only when its saved due time has arrived, at least six hours after the previous cycle started. An unfinished cycle can continue on a later wake before that due time, retaining its original identity, scope, gift results and history cursor. Early wake-ups with no continuation read the saved checkpoint and exit without provider requests or database writes. A later wake-up can catch a missed trigger without replaying every missed interval. A manual **Run workflow**, leaving **scheduled** unchecked, can still retry an incomplete or failed check before it is due, using the same operation and safeguards; it cannot repeat a completed check early. Scheduled dispatches explicitly set that input to true and never receive the manual retry exception.

Cloudflare checks for an active workflow and recent dispatch before sending another request. These checks reduce duplicates but are not an exactly-once guarantee: two triggers can race. GitHub's shared concurrency group and the monitoring worker's durable lease, checkpoints, and due-time checks remain the safeguards against overlapping provider work. GitHub still executes the 20-minute runner; the independent trigger avoids relying solely on GitHub's cron delivery, but cannot bypass a GitHub outage, queued runner, disabled workflow, or environment approval.

The runner retrieves the app's canonical deployed source, requires the version-1 private monitoring access protocol, scoped-history capability and personal-analytics capability, adds the reviewed local worker and its fixed bridge to an administrative `/run` request, and resolves only their module dependencies. The scoped-history capability (`PRIVATE_BACKGROUND_SCOPED_HISTORY_VERSION=1`) guarantees that history jobs preserve trusted monitored targets and validate their scope before resuming. Personal analytics (`PRIVATE_BACKGROUND_PERSONAL_ANALYTICS_VERSION=1`) requires the guarded remembered-session refresh implementation. The runner and bridge reject older access-version-1 runtimes that lack either required capability. It does not publish modules, change the deployed manifest, or install a public endpoint. Application credentials and private configuration are read from the existing deployed app; no local configuration files are uploaded. The bridge also requires a fixed administrative context marker so an accidental Mini App endpoint publication cannot grant ordinary callers owner access.

Each invocation has a random runner identifier, a 20-minute deadline, and at most 200 administrative requests. Individual requests have a 90-second timeout and bounded response sizes. Waiting states honor their saved `retry_at`. When the provider deadline has already passed, a running step can continue without an extra one-second runner delay; provider pacing still applies. After a transport timeout, lost connection, or transient hosting failure, the runner can make up to three read-only recovery requests within those same bounds. It reads the saved checkpoint before continuing, waits for any active lease or provider cooldown, and uses the same runner identifier. It never repeats the first tick's manual retry exception. An already finished or paused checkpoint stops recovery; invalid responses, access errors and explicit remote execution failures stop safely. A timeout does not imply that the most recent remote step was rolled back.

The dashboard receives an activity expiry and the current execution segment's deadline. A saved running checkpoint shows **Waiting for recovery** when its next permitted request or active lease has expired by more than one minute. A yielded continuation is shown as incomplete, with its continuation eligibility, rather than claiming active work. Status and Price rules age this display locally, even if another status read fails. Reading status never renews activity or changes the checkpoint; only another eligible runner can claim a continuation. Provider cooldowns remain respected, and the display does not claim a check completed.

Cloud gift checks target only retained gifts with enabled, unpaused rules. They use a five-minute window; ordinary dashboard refreshes keep their existing two-minute limit. Recognized candidates and unmonitored gifts do not consume the cloud check's TON work.

If the remembered Marketapp login is expired or rejected during a cloud gift check, the check falls back to TON without clearing the login itself. Clearing it would change the session generation captured by the same run and incorrectly report `scope_changed`. Foreground account actions still clean up invalid sessions; a real logout, wallet change or credential change still invalidates cloud work. Personal analytics needs a usable remembered login and reports its outcome separately.

Automatic dashboard startup can reuse a completed cloud gift check for up to one hour from its original start, without making another provider request. Reuse requires verified ownership/status for the entire current portfolio, matching wallet and monitored targets, unchanged personal evidence and source TON result, and no crossed rental expiry. A subset or incomplete cloud check cannot stand in for a full portfolio check. Original observation dates remain visible, manual Refresh requests new evidence, and the foreground never joins or advances a live cloud session. Validated portfolio scope revisions are saved with the same checkpoint CAS so unchanged scopes need no repeated history scan.

If a cloud gift check reaches its time window, the worker can continue the same saved TON traversal once within that cycle, for up to five more minutes. Completed results, the cursor, and the shared 20-request allowance are preserved; the continuation does not reset provider or daily budgets. At least five minutes remain reserved for rental history. Provider cooldowns, active leases, changes to the monitored gifts, and a manual Stop still prevent an unsafe continuation.

If the bounded continuation cannot finish, the result stays incomplete and the next cycle starts with the first unfinished TON check. A website count showing every gift checked does not mean the additional TON verification is complete. Results from different six-hour cycles are not combined into a falsely fresh, completed check.

History collection checks only collections containing retained gifts with enabled, unpaused rules, using a 30-, 60-, or 90-day window. Each execution segment permits at most 100 collection steps and three invocation resumes. Reaching a segment limit saves a continuation instead of advancing past unfinished history. A different scheduler runner can continue the same cycle without waiting six hours, with a fresh 20-minute segment; at most 12 segments and four hours are allowed for the whole cycle. The original cycle identity, wallet/credential/session scope, monitored targets, history cursor and freshness watermark remain fixed. A live lease, changed scope or targets, replaced history job, explicit Stop or exhausted provider allowance cannot be bypassed. Shared account limits are never reset by continuation. This does not mark unmonitored collections as freshly checked or change manual full-portfolio scans. An older unfinished traversal is adopted only when it is acknowledged as this worker's job and its frozen targets still match. After finishing that older traversal, the worker checks the recent head before treating history as current. Each new cycle sets its next automatic due time six hours after its actual start; continuation does not move that clock. Idle completed checks retain the existing one-hour scheduling allowance before showing Check delayed.

New history jobs can reuse a completed, ordered and scope-verified coverage proof when it covers the requested window and its last full scan is less than seven days old. Reused streams scan from 48 hours before the previous checked-through time, bounded by the requested window. Missing, invalid, expired or narrower proofs require a full scan. Only successful, ordered and scope-verified completion publishes coverage; an incremental pass does not renew the full-scan date. Existing saved jobs retain their frozen plans and cursors. Multiple collections can become due together, and a first reconciliation, increased activity or other account usage can still exhaust the shared allowance.

A history job paused at the daily allowance retains its progress. A later eligible cycle can resume that acknowledged job after fresh status confirms available capacity; an elapsed request-spacing timer alone is insufficient. Resume rechecks the same atomic request allowance, provider cooldown and scope guards. While capacity is exhausted, the cycle can still refresh personal analytics and evaluate rules, but remains partial and does not prepare the dashboard cache. The rolling 500-request limit is not reset or increased.

Foreground comparison cycles have separate bounds: listings every 24 hours with at most 200 attempts, rentals every six hours with at most 100. A completed cloud or manual check covering every requested collection also defers a new automatic cycle for that source interval; a partial monitored subset does not. They run in chunks of at most 20 attempts and 60 seconds, starting with missing and oldest collections. Automatic listings stop before spending the last 100 requests of the account's rolling allowance. This leaves capacity for monitoring and rental checks; it neither raises provider limits nor guarantees that external capacity is available. Explicit manual collection retains its normal limits.

An inactive listing-price scan that ended at its request or time allowance does not block a separate cloud rental-history check. Automatic listing scans can also yield after reaching their cycle allowance or preserving the monitoring reserve. This also covers a scan left marked running or queued when both its saved invocation deadline and request lease have expired. Its saved data and cursor remain available for manual Resume. Explicitly stopped scans, active requests, and unfinished manual rental-history scans still block that switch.

For longer idle rules, the app retains a bounded record of overlapping, completed and verified history coverage for each unchanged availability baseline. This lets continued monitoring support rules up to 365 days without repeatedly downloading an ever-growing history window. The latest completed coverage must still include the latest gift observation. Missing or ambiguous history cannot extend that coverage, and a changed availability baseline starts it over.

Rule evaluation buffers at most 25,000 history records and 16 MiB of their raw JSON across the portfolio. If gifts excluded from the final portfolio consumed that allowance, it releases the buffer and rereads the same saved revision for the retained gifts. If retained history still exceeds either limit, evaluation reports incomplete history and blocks price suggestions and approvals, including increases based on previously saved demand. Existing data remains saved.

Before price-rule evaluation, each eligible cycle also attempts one personal analytics refresh using the owner's existing encrypted remembered Marketapp login. It first captures a 365-day report if there is no annual seed. Once seeded, it normally captures a 30-day report, allowing compatible archived periods to accumulate beyond one year. If the latest included date is more than 30 days old, it requests a 365-day catch-up instead. This does not reconstruct dates omitted by the provider or invent per-gift history from wallet totals.

Personal analytics has its own checkpoint and hosting request, with a 60-second work bound and at least 60 seconds reserved on the server for rule evaluation. The driver also budgets time already spent downloading source and reserves two 90-second requests, the dashboard preparation/confirmation allowances and a one-second handoff margin. When another full stage cannot fit, it checkpoints a continuation while time remains for a separate bounded save; a later scheduler runner resumes the same stage. A new continuation-enabled cycle does not record a budget-skipped analytics outcome merely because its current invocation is ending. Old saved ledgers remain readable. A source download that consumes the available work budget causes a read-only status check without claiming new provider work. The refresh retains the shared website lease, request limits and 15-minute fresh-report guard; a saved report is reused after a lost response. A missing/expired remembered login requires reconnecting Marketapp in the app. Pausing monitoring, changing the wallet or credentials, or losing the worker lease fences requests and writes. All price changes still require wallet approval.

Logs and saved cloud status separately include `personal_analytics` with `saved`, `fresh`, `busy`, `limited` or `unavailable`, the selected report period and safe timestamps/reason where available. A gift/rule cycle can be complete while analytics is unavailable or rate limited; inspect this separate outcome to establish that all-time history was refreshed. Later eligible cycles retry normally. Analytics refresh runs only for an enabled monitoring cycle, so pausing all price rules or disabling the scheduler also pauses these automatic captures.

Logs contain fixed status names, counts, dates, and sanitized failure categories, stages and HTTP status codes. Provider responses, addresses, gifts, credentials, private source, and remote error messages are not printed or uploaded as artifacts. A `partial` result means the runner reached a bound or saved work for a later wake-up; `blocked` or `failed` makes the workflow fail so the operator can investigate.

Execution diagnostics additionally allow a bounded host duration (`execution_ms`), an exact recognized CPU/memory/time limit (`execution_limit`), fixed guard codes (`execution_code`), and the preparation phase (`prewarm_phase`). Unknown text, host logs and arbitrary error parameters are discarded. An expired cache deadline reports `BACKGROUND_PREWARM_TIMEOUT`; a changed completed run or lost ownership retains the separate lease/scope failure.

The administrative bridge returns known preparation and confirmation failures as a fixed `failed` result with an allowlisted `execution_code`, so a host-generated exception stack cannot hide their meaning. For example, confirmation of missing or stale artifacts reports `BACKGROUND_PREWARM_INCOMPLETE`; it never becomes `prepared`. Unknown exceptions still propagate through the host error path. The runner preserves the original preparation failure, attempts each supported build stage at most once, and performs at most one independent read-only confirmation when permitted. No raw exception messages, stack traces or provider text are included.

After this runner's completed check is acknowledged, a deployed runtime advertising `PRIVATE_BACKGROUND_DASHBOARD_PREWARM_VERSION=1` can prepare one compact dashboard in a separate, best-effort request. It uses the most recently built valid pricing selection (or Actual rentals, Last 30 days), retaining account, wallet, reset and recognition boundaries. The request gets a 30-second transport allowance and a 25-second work deadline, must fit the existing runner budget, and is not retried. It reads saved records and writes only derived dashboard cache entries; it cannot refresh providers or change prices or monitoring results. Logs separately report `dashboard_preparation: prepared`, `skipped` or `failed`. A preparation failure leaves the successful monitoring outcome intact. Older runtimes skip this optional step. Both the updated Telegram runtime and the reviewed runner on the default branch are required to enable it.

With `PRIVATE_BACKGROUND_DASHBOARD_CONFIRMATION_VERSION=1`, that build only stages the caches. A second, strictly read-only request has its own 10-second work deadline and 15-second transport allowance. The runner reserves both requests inside its existing 20-minute/200-request budget. Building retains the 25-second deadline, with headroom for final guards; it does not reread and reproject the full artifacts at the end of that same request.

With the additional `PRIVATE_BACKGROUND_DASHBOARD_PREPARATION_VERSION=2` capability, building is split into a `basis` request and a `cards` request, followed by the same independent confirmation. The driver reserves all three requests and 75 seconds inside its existing budget, including time already spent downloading source. Each builder retains its own 25-second work deadline and 30-second transport allowance; confirmation retains its 10-second/15-second bounds. The bridge accepts only `prewarm_only: true` with `prewarm_stage: "basis"` or `"cards"` and binds that exact phase to the trusted runtime context. The basis stage replays saved history and saves the shared rental-window basis; the cards stage validates and uses that saved basis without replaying history. Neither stage can report `prepared`. Older confirmation-capable runtimes retain the combined build, and legacy prewarm remains supported.

Only confirmation can report `prepared`. It validates both the selected cards and the shared rental-window basis when applicable, including persisted hashes, current source revision, wallet/credential/session identity, reset floor, clocks and exact completed-cycle attribution. It cannot rebuild, initialize a session, write storage or call providers. An ambiguous basis response permits one cards attempt; if the basis was not saved or has become stale, cards cannot rebuild it. An ambiguous cards or legacy combined-build response can still be followed by bounded confirmation without repeating a build. Known scope/access/lease/rules failures stop safely, and missing or stale artifacts cannot be certified. Logs distinguish `basis`, `cards`, and `confirm` phases, preserving each original failure even if the final confirmation reports `preparation_recovered: true`. Runtimes without confirmation retain their previous single-request behavior.

Compact archive reads target at most 512 KiB of serialized database rows per transfer, including escaped text and conservative metadata overhead, to reduce preparation round trips. The 800-row query cap, 800-record/1 MiB visitor batches, exact record ordering and scope checks remain unchanged. Larger legacy records use the existing bounded chunk reader. This is an application transfer bound, not a stated hosting guarantee; preparation still enforces its 25-second deadline.

## Credential trust and repository protection

`TGCLOUD_TOKEN` is the full Telegram app administration credential, **not a restricted monitoring token**. Someone who obtains it can administer the app beyond this worker. The worker intentionally uses a narrow fixed operation, but that does not reduce the credential's underlying authority.

Use the protected GitHub environment named `price-monitoring`. Restrict it to the repository's default branch and protect that branch against unreviewed pushes. Review changes to the workflow, worker, runner, and imported administrative helpers before merging. Required reviewers can protect the initial rollout; if required for every job, each scheduled run will wait for approval and will not be unattended. GitHub documents these [environment protection and secret-access controls](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments).

The committed workflow permits only `resu12/gift-rent-check` and its default branch. It has no pull-request trigger, uses read-only GitHub repository permissions, pins the checkout and Node actions to immutable revisions, retains no checkout credential, and exposes the Telegram secret only to the worker step. It runs directly on Node 24 without installing packages or running dependency installation scripts. Do not add debug dumps, shell tracing, source artifacts, or arbitrary user-supplied commands to this credentialed job.

The optional Cloudflare scheduler holds only a separate fine-grained GitHub token restricted to the selected repository with **Actions: read and write**. It never receives `TGCLOUD_TOKEN`, Telegram bot credentials, wallet data, or Marketapp credentials. The trigger's code fixes its workflow and branch; the GitHub token itself still grants broader Actions access within that one repository. Keep the existing workflow and environment protections in place. See the [scheduler deployment and rotation instructions](cloudflare-scheduler.md).

## Activation

The workflow is inert until explicitly configured. Adding these files alone does not start monitoring.

1. Publish the runtime implementing the required private monitoring access protocol, scoped-history and personal-analytics capabilities, and associated status-display changes using the normal deployment checks. Verify it with the updated runner's read-only `--check`, then merge the reviewed worker, runner, and workflow into the default branch **before enabling the schedule**. For an already active schedule, deploy the capability-bearing runtime before merging the updated runner: the additive capabilities preserve the existing access version, so older runners remain compatible during review, while the updated runner rejects older runtimes. Advertise each capability only in a runtime implementing its guarded operation; adding markers to an older runtime is insufficient. The worker itself is supplied to `/run` and does not consume another deployed module slot.
2. Create the `price-monitoring` environment in **Settings → Environments**. Limit deployment branches to the default branch and configure the review protections appropriate for the rollout.
3. In that environment, add secret `TGCLOUD_TOKEN` with the app's existing administration credential and variable `TGCLOUD_APP_ID` with the explicit numeric app ID. Never place the token in a repository variable, file, issue, workflow input, or command-line argument.
4. Create the **repository-level** Actions variable `BACKGROUND_MONITORING_ENABLED` with value `true`. The job condition reads this repository variable before environment variables become available. Remove it or set it to `false` to disable future runs.
5. Use **Actions → Background price monitoring → Run workflow**, on the default branch. Inspect the sanitized status and the app's monitoring status/approval queue. An expired Marketapp login, missing required data, quota exhaustion, or a paused rule may prevent useful work even when the workflow is configured correctly.
6. To add the independent trigger, first merge the reviewed workflow containing the boolean `scheduled` input and its manual-retry guard into protected `main`. Then follow [Cloudflare scheduler activation](cloudflare-scheduler.md#deploy-and-activate). Do not enable a trigger against an older workflow that treats every dispatch as a manual retry.

For a local read-only connection and source-layout check, provide `TGCLOUD_TOKEN` securely through the process environment and run:

```sh
node serverless/tools/run-background-monitoring.mjs --app-id YOUR_NUMERIC_APP_ID --check
```

`--check` contacts only the official Telegram `/manage/get` endpoint, verifies the deployed version-1 monitoring access protocol, scoped-history and personal-analytics capabilities, and validates the administrative dependency bundle. It does not execute the worker, create jobs, refresh providers, or prove that a future monitoring cycle will complete. It works before enabling the schedule. The ordinary CLI requires `BACKGROUND_MONITORING_ENABLED=true`; otherwise it exits as `disabled` without contacting Telegram. It accepts no endpoint, SQL, user identity, source path, or arbitrary operation argument.

## Pausing and recovery

Pause all rules or individual gifts in the app to stop their rule monitoring. Set the repository variable `BACKGROUND_MONITORING_ENABLED=false` to prevent future monitoring jobs from either trigger, or disable the workflow. If Cloudflare is active, also set its `SCHEDULER_ENABLED` variable to `false` to stop dispatch requests; this alone leaves the GitHub fallback running. To stop a running job immediately, cancel it in GitHub; a remote step already in progress may still finish and save its checkpoint. Uncertain in-flight work remains subject to the saved lease rather than being force-cleared.

Runs are serialized with `cancel-in-progress: false`; a new invocation does not cancel one already holding a checkpoint. After resolving a failure, use **Run workflow** with **scheduled** unchecked to retry a failed, blocked, partial, or previously paused check without waiting for the next six-hour slot. The workflow sets the manual-retry flag only when `github.event_name == 'workflow_dispatch' && inputs.scheduled != true`, and the runner sends it only on its first tick. It cannot bypass a successful check's normal due time, an active lease, a provider cooldown, or rules that remain paused. Repeated manual retries are rate limited. Do not delete checkpoints, lift request limits, or reset provider budgets to force progress. If the administration secret may have been exposed, rotate it through the hosting platform and update the environment secret before re-enabling the workflow.

GitHub schedules are best effort. Runs can be delayed or dropped under high load, and public-repository schedules are disabled after 60 days without repository activity. Scheduled workflows run only from the default branch. The independent Cloudflare trigger provides more frequent catch-up opportunities, while the hourly GitHub schedule remains available if that trigger is unavailable. With punctual wake-ups and an available GitHub runner, a new automatic check can start within 15 minutes after eligibility with Cloudflare, or within an hour with GitHub alone; these are schedule intervals, not delivery guarantees. Check the Cloudflare trigger logs and GitHub Actions separately, and re-enable a disabled workflow when needed. See GitHub's [schedule behavior and limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Long gaps, incomplete rental history, or unavailable ownership evidence can delay suggestions or restart an idle observation period. Active gift rules need a maximum observation gap longer than the six-hour schedule; even an exact six-hour gap can be exceeded by scheduling or provider delays. The app warns about enabled, unpaused gifts whose effective gap is six hours or less and recommends the default 36 hours. It does not change saved settings automatically. The worker preserves the conservative rule checks instead of inventing activity during missed checks. No hosted storage allowance or successful unattended run is implied by installing this workflow.
