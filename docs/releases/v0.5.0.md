# Gift Rent Check v0.5.0

**Development / invitation-only beta — mark this GitHub release as a prerelease.**

This release adds retained rental analytics, improves startup and simplifies the interface. The app changes are deployed through Telegram revision 123. Publishing this source release does not enable open registration, change access settings or reset saved data.

## Highlights

- **All time analytics:** Overview opens with saved history. Overlapping daily reports count once, older history survives normal cleanup, and missing or partial periods remain visible.
- **Gift and collection reports:** Marketapp's Top items and By collection match the selected report period, with saved pictures, search, sorting and expandable exact figures. Each gift's details also shows its saved All time rentals. Collection totals remain independent of the ranked gift subset.
- **Invited-user Marketapp login:** configured beta accounts can use their own wallet-approved login for analytics and gift refresh, with optional encrypted remembered sessions and TON fallback. API keys and account data remain separate.
- **Faster startup:** dated saved data can appear before the current view is calculated. Secondary screens and wallet controls load on demand. Telegram SDK delays no longer block the startup timeout, and completed gift checks do not wait for unrelated comparison updates.
- **Less clutter:** Pricing, My gifts, Overview and Status focus on prices, totals and freshness. Secondary dates, counts and explanations are expandable; warnings, connection controls and missing figures remain accessible.
- **More reliable tracking:** price changes survive source updates, verified rental starts can appear before payment history arrives, and refresh/cleanup controls distinguish waiting from failure.
- **Operator tools:** encrypted backup verification, synthetic capacity drills, registration readiness checks, and an optional lossless database index support safer operation. These tools do not establish a hosting quota or a verified hosted recovery process.
- **Upgrade tooling:** storage/analytics setup, backup and readiness checks use smaller dependency bundles that fit a full deployed app and preserve its private configuration.

All-time figures cover saved reports, not an independently verified lifetime. Volume is before fees and royalties; unavailable payments and daily rates remain unknown. The app never changes rental prices or signs transactions.

## Upgrade from v0.4.0

Retain the deployment's existing private configuration, invitation settings and encryption key. Keep open registration disabled. Confirm an appropriate database backup/recovery method, stop refreshes during setup, and run the tests, both builds and destination preflight before publishing. Do not rotate or reset live encryption nonce counters as part of this upgrade.

The bundled atomic backup exporter has a bounded output size and did **not** complete against the larger development database. Treat a failed backup as a failed backup, not a recovery guarantee. See [backup and recovery limits](../backup-recovery-and-capacity.md).

1. Publish the additive schema, inspect the proposed migration and apply only the safe migration:

   ```powershell
   node serverless/tools/manage.mjs --action publish-schema --app-id YOUR_APP_ID
   node serverless/tools/manage.mjs --action migrate-check --app-id YOUR_APP_ID
   node serverless/tools/manage.mjs --action migrate-safe --app-id YOUR_APP_ID
   ```

   New tables retain private/public daily analytics, gift and collection reports, public gift-refresh summaries, and the optional inline-event selector. The bounded All time reader also needs four capture indexes on the private/public gift and collection archives; apply them before publishing the runtime. Existing data is retained. Review unexpected destructive operations instead of applying them.

2. Install accounting and compact operational triggers, then analytics archive triggers:

   ```powershell
   node serverless/tools/compact-storage.mjs --action setup --app-id YOUR_APP_ID --owner-id YOUR_OWNER_ID
   node serverless/tools/install-analytics-daily-storage.mjs --action install --app-id YOUR_APP_ID --owner-id YOUR_OWNER_ID
   ```

   These additive installers preserve current counters and existing accounted data. Resume an interrupted setup with the same command. Analytics setup must report `ready: true` and 40 archive triggers, including explicit empty-table availability. Deployments with the earlier 24 triggers rerun this installer, then both backfills after publishing the runtime. Nonempty unaccounted tables or unexpected trigger definitions require investigation rather than a reset.

3. Publish the tested runtime and frontend so new imports preserve gift and collection history before old snapshots can be replaced:

   ```powershell
   node serverless/tools/manage.mjs --action publish --app-id YOUR_APP_ID
   ```

4. Backfill saved reports in both scopes:

   ```powershell
   node serverless/tools/install-analytics-daily-storage.mjs --action backfill --scope private --app-id YOUR_APP_ID --owner-id YOUR_OWNER_ID
   node serverless/tools/install-analytics-daily-storage.mjs --action backfill --scope public --app-id YOUR_APP_ID --owner-id YOUR_OWNER_ID
   ```

   If a scope is incomplete, repeat its command with the returned `--after` cursor until `complete: true`. Backfill preserves the source reports and makes no provider requests. Reports without gift/collection tables need a normal analytics refresh after publication.

5. Optionally install the faster inline-event selector:

   ```powershell
   node serverless/tools/install-inline-record-index.mjs --app-id YOUR_APP_ID --owner-id YOUR_OWNER_ID
   ```

   Repeat with the returned `--cursor` until `complete: true` and `definitions: 8`. This copies only event identifiers, preserves original evidence, and uses bounded batches. Readers retain their existing scan until every required index/trigger is verified. Preserve these administrator-managed indexes during future schema migrations.

Use the [analytics guide](../personal-analytics.md), [gift/collection guide](../per-gift-rental-statistics.md) and [storage guide](../storage-maintenance.md) for retention and cursor details. Older installations must complete the [v0.4.0 prerequisites](v0.4.0.md) first. Do not roll back to older writers after installing the new archive/compact-storage formats.

## Validation

- Python: **1,429 passed**; one upstream Starlette TestClient deprecation warning.
- Frontend: **859 passed**; TypeScript and both local/serverless production builds passed.
- Backend: **1,245 passed**, with two Windows symlink checks skipped because symlink creation was unavailable. This includes administrative-bundle checks, v0.4.0 upgrade import compatibility and 13 empty-table persistence regressions. The original 24 archive trigger definitions remain unchanged.
- Frontend/backend checks and builds used a source-only copy with frozen offline dependencies and no private deployment configuration. The final backend suite includes the upgrade-tool fixes.
- Versions, local documentation links and candidate paths were reviewed; private configurations, credentials and operational data remain excluded.

These are local results. GitHub Actions must still pass on the pushed commit.

Live revision 123 changed only static assets: all 32 served files matched the tested build and all 100 backend/schema modules were unchanged. This verifies publication, not a new wallet-login or provider test.

## Beta limits

- Open registration remains disabled pending verified hosting capacity, recovery and provider/operator approval. Publishing on GitHub does not open the hosted service.
- Marketapp website login and page parsing remain experimental. Provider changes or expiry can require reconnection; saved data is kept on failure.
- Per-gift and per-collection All time coverage can differ from the daily chart and from each other. Missing periods are never treated as zero income.
- Telegram All time reads at most 2,000 daily records, 400 gift-report rows and 600 collection-report rows per dashboard request. Large archives show a limited-history notice; all stored rows are retained. The 30-day and yearly source reports are unaffected.
- Storage budgets are application safeguards, not verified Telegram quotas. Backup size limits and hosted recovery remain deployment-specific constraints.
- Foreground refreshes can pause for provider limits or when the app closes. Continuous background collection is not promised.
